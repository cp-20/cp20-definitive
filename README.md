# cp20.dev — definitive edition

「しーぴーのスタンプ帳」（クローバー色の机に置いたルーズリーフ）をモチーフにした、Cloudflare Workers向けのポートフォリオ。SolidJS 2.0.0-rc.10 のコンポーネントから全ページを静的HTMLに生成し、訪問者がページにシールを貼れるFirebase Realtime Databaseを組み合わせています。

## 開発

Node.js 24以上。

```sh
npm ci
npm run build
npm run dev:worker
```

`http://localhost:8787` はCloudflare Static Assetsの本番相当プレビュー。`npm run dev` で `http://localhost:4321` の編集用サーバーを起動できます。シールは開発中も専用Firebase DBへ接続し、閲覧者間で共有されます。テスト用に貼ったシールははがしてください。

```sh
npm run sync   # 記事・GitHub・おすすめ曲/漫画・サムネイルを取得
npm test       # 振る舞いのテスト（収集・OG解析・画像・シールの楽観的更新と保存・配置計算など）とビルド結果の検査
npm run cache:images # 画像キャッシュだけ更新（通常はsyncが実行）
npm run check  # 型検査（TypeScript 7 のネイティブ版 tsc）
npm run rules  # database.rules.json をページ一覧から再生成（--check で差分の検査のみ）
npm run build
```

初期データを同梱しているため、収集なしでもビルドできます。

### 書体のお試し（一時的）

実際のページで書体の組み合わせを比べるための一時的な仕組みです。どのページでも URL に `?font=<名前>` を付けて開くと、その組（`current` いまの組、`yusei-kaku` 手書き＋端正なゴシック、`klee` ペン字のノート、`kiwi` やわらかい丸、`mincho` 明朝の見出し、`zenkaku` 上品なゴシック、`lineseed` くっきりモダン、`ud` 読みやすさ重視）に切り替わり、選んだ組は localStorage に残ってほかのページや再読み込みでも続きます。同時に左下（スマートフォンでは下のタブの上）に「書体：…」のパネルが出て（`?font` だけなら組はそのまま）、見出し・文・数字と欧文・コードの書体が並んだ一覧から選び直せます。`?font=off` かパネルの「お試しをやめる」で元に戻り、パネルも消えます。組は `src/site/font-trial.ts`（各役の書体・太さ・欧文の size-adjust・字間）、読み込みとパネルは `src/site/font-trial-panel.ts` にあり、書体は @fontsource のスタイルシートを選んだときにだけ読み込むので、お試しをしていない訪問者には（`App.tsx` の数行のほかは）何も増えません。組を決めたら、この2つのファイルと `App.tsx` の呼び出し、`scripts/build/fonts.ts` の除外、使わない @fontsource のパッケージを外し、選んだ書体をサイトの書体（`fonts/`、`scripts/build/fonts.ts` でサブセット化）に置き換えます。

## 本番公開の初期設定

**公開はCloudflare Workers Builds（CloudflareのGit連携）で行います。`main` へのpushごとにCloudflare上でビルドしてデプロイします。GitHub Actionsは記事などの定期収集とスナップショットのコミット、PR・`main` の検証（`CI`）、Firebaseルールのデプロイ（専用DBのみ。下記「ルールの更新」）を担当します。Cloudflareの認証情報は持ちません。**

2026-10-06に `cp-20/cp20-definitive` の `main` とWorkerの接続を設定済みです。公開URLは [cp20-definitive.cp20.workers.dev](https://cp20-definitive.cp20.workers.dev/)。ルートディレクトリは `/`、ビルド・デプロイコマンドは下記のとおりです。非本番ブランチの自動ビルドは無効です。

1. このフォルダをGitHubリポジトリの `main` に配置。
2. Actionsにスナップショットを書き戻す権限を許可。ブランチ保護を使う場合も更新経路を確保。
3. Cloudflareダッシュボードの **Workers & Pages → Create → Import a repository** で `cp-20/cp20-definitive` を接続し、次のように設定。
   - Worker名：`cp20-definitive`（`wrangler.jsonc` の `name` と一致させる。違うとビルドが失敗します）
   - Production branch：`main`
   - Build command：`npm run verify`（`npm run check`・`npm run build`・`npm test` を順に実行。テストはビルド結果も検査するためビルドの後。ViteのビルドはTypeScriptの型を検査しないため、`npm run build` だけだと型やテストが壊れた変更も公開されます。2026-10-06の接続時は `npm run build` で設定したため、ダッシュボードの Settings → Build で変更してください）
   - Deploy command：`npx wrangler deploy`
   - Node.js：`.node-version` の 24（Workers Buildsの既定も24）
   - 任意：Non-production branch builds を有効にすると、ブランチごとのプレビューURLで確認できます。
4. workers.devで確認後、CloudflareのCustom Domainsで `cp20.dev` を接続。

ドメイン・既存本番サイト・みんなのものさしリポジトリの公開設定は変更していません。canonical / sitemap / robots / RSSは本番予定の `https://cp20.dev` を指します。

### traPブログ

traPの記事は公開の著者ページ `https://trap.jp/author/cp20/` から、各ページの `<link rel="next">` をたどって最後のページまで読み、タイトル・URL・公開日だけを取得します（1ページ12件、2026-11時点で3ページ・34件）。途中のページの取得失敗、記事のない・想定外の次ページ、取得中の新規投稿で同じ記事が2ページに出た場合は、一部だけの一覧を保存せずに失敗とし、次回の定期実行で取り直します。キーは不要です。公開時刻は著者RSS（最新15件）から補い、RSSにない古い記事は著者ページに出る日付（日本時間）を使います。カードの形式が変わった場合も失敗として前回のスナップショットを維持し、正常な全件取得後は一覧から消えた記事を除去します（作品の関連記事に指定した記事は保持）。

以前は Ghost Admin API を使っていましたが、管理APIは traP SSO の内側にあり（Ghostに届く前にHTTP 307でログインへ転送）、定期収集では一度も成功していなかったため廃止しました。

ローカルで収集する場合は `npm run sync`。GitHub APIの上限を増やしたいときだけ `.env.example` を `.env.sync` にコピーして `GITHUB_TOKEN` を設定します。

### 自動更新

6時間ごとにGitHub Actionsで取得し、公開はCloudflareのGit連携が行います。普段は元のサービスへ記事を投稿するだけです。

| 対象                             | 取得元 / 動作                                                                                                          |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| Zenn・Qiita                      | 公開APIを全ページ取得                                                                                                  |
| note・sizu.me・blog.cp20.dev     | RSS。配信範囲から外れた過去記事を保持                                                                                  |
| traP                             | 公開の著者ページを全ページ取得（公開時刻は著者RSSで補完）                                                              |
| 公開コード                       | GitHub API。fork・archived以外の最近更新したリポジトリ                                                                 |
| 好きな曲・漫画                   | 2026版の公開 `featured-tracks` / `featured-series` データ                                                              |
| 漫画のサムネイル                 | 公式掲載ページの `og:image`。失敗時は前回URLを保持                                                                     |
| 作品・記事のOG画像と作品アイコン | 元の公開ページから取得し、画像本体をダウンロード。実画像の寸法を記録。正常取得は週1回、新規・失敗分は6時間ごとに再取得 |
| YouTubeのサムネイル              | おすすめ曲の動画IDに対応したYouTube画像                                                                                |

ネットワークの部分障害では前回データを保持し、全記事ソース失敗時は処理を失敗させます。公開データに差分がある場合は型検査とビルドで確認してから `main` にコミットし、そのpushでCloudflareが再デプロイします。チェック日時だけの更新は `[skip ci]` を付けてコミットし、長期無活動でのActionsスケジュール停止を避けます。収集・テスト・ビルドは読み取り専用のジョブで行い（`npm ci --ignore-scripts`、認証情報を `.git/config` に残さない）、検証済みの生成物だけを書き込み権限のある別ジョブがコミットします。actions はコミットSHAで固定しています。traPの記事が前回の半分未満に減った取得は失敗扱いにして前回データを保持します。意図した削除なら手動実行で `allow_trap_shrink` を有効にしてください。RSSの不正な記事は1件だけ除外し、XMLで使えない制御文字はタイトルから除去します。OG解析は `<head>` 内を先頭1MBまでしか読みません。スケジュールの遅延・外部サービス障害まで保証するものではありません。

自動取得できない経歴や説明を推測して更新することはしません。学年は各経歴の発生時点の値を保存しています。曲・漫画の「好き」は2026版に本人が選定したものです。視聴履歴を推測しません。

## フォルダ構成

- `src/site`：ページ一覧・ルーティング・ページ内遷移・タブ（`Shell.tsx`）。
- `src/content`：記事・作品・画像の整形（クライアントに渡す形）。
- `src/components` / `src/pages`：共有コンポーネントと各ページ。
- `src/stamps`：シール機能一式（UI・Firebaseクライアント・純粋なロジック・型・テスト）。
- `src/data`：JSONのデータと内容の定義（経歴・漫画の表紙）。
- `scripts/build`：ビルド後の静的HTML・RSS・sitemap・フォント・ライセンス表示。
- `scripts/sync`：定期収集（記事・trap.jp・リンクのプレビュー・画像キャッシュ・収集の健全性）。
- `scripts/firebase`：DBルールの生成とエミュレーターでの検証。
- `scripts/qa`：手元のブラウザ検証。

scripts はNodeの型除去でTypeScriptをそのまま実行します（tsx等は不要）。

## 内容の構成

- トップ：名乗りと事実の2行、Twitter と GitHub、実績3つの付箋（`editorial.ts` の `highlightIds`。各行が `/about#<id>` でその経歴のダイアログを開く。続いている経歴（`ongoing`）は始めた月を添える）→ 代表作3つ（作品一覧と同じカード）と「最近つくったもの」（代表作以外で、始めた日が新しい2つを1行ずつ）→ 最近の記事（その年のかいた日カードと新しい3本）と好きなもの（曲と漫画を1つずつ、`/about#music`・`#manga` へ。漫画は表紙を切らずに全体を貼り、スマホでは曲の切手が表紙の横の幅いっぱいに並んで、ほぼ同じ高さの1組になる）。iPhone 13 の最初の画面に、名乗りから実績までと「代表作」の見出しが入る。スマホではシールのボタンが下のタブの列の右端にあり、本文には重ならない。
- 代表作：ダイススペック v2、自作Cコンパイラ、みんなのものさし（`editorial.ts` の `featuredIds`）。カードの絵は作品の OG 画像（画面は作品のページで見せる）。カード全体は作品のページへのリンクで、題名の後ろのシェブロン（ホバーで 3px 進む）がその印。代表作のカードの下のボタンは外（作品そのもの）へ出るもので、行き先をそのアイコンと一緒に書く（サイトならホスト名「dicespec.app ↗」、リポジトリなら GitHub のアイコンと `cp-20/c-compiler`。長いホスト名は省略記号で切る）。ボタンにホバーしている間、カードの蛍光ペンとシェブロンは動かない。作品のアイコンは白い角丸の台紙（1px の鉛筆線）に載せ、透明・白地・色地のアイコンを同じ形に揃える。端まで描かれたアイコンは `works.json` の `iconInset` で余白を広げる（東工大講義リスト）。
- 残りは作品一覧から閲覧。作品一覧は代表作3つ、始めた年ごと（新しい順、年の見出しは消印）、主催したイベント、歴代の cp20.dev（毎年変えたフレームワークを添える）、GitHub の最近の動き（説明のあるリポジトリ6件まで）の順。
- 作品のページは名前・要約・事実（成果・役割・期間・公開の状態。成果には Lucide の Sparkles を朱で添える）・行き先で名前を変えるボタン（サイトを開く／GitHub で見る／VS Code Marketplace で見る／開催記を読む。公開を終えたものはボタンなし）・画像を最初に並べ、そのあと本人の制作メモ・関連記事・一覧で前後の作品。
- 作品：`src/data/works.json`。新作の説明はユーザー指定の公開サイトとREADMEを確認。任意の項目は値があるときだけ表示します：`summary`（作品ページの要約）、`role`（役割。1人でつくったものは「1人で企画・デザイン・実装」）、`outcome`（数字や賞のある成果。分かっている数字だけ）、`status`（`ended` 公開終了／`members-only` traP 部員向け）、`kind: "event"`（主催したイベント）、`links`（公開を終えた作品のボタンの代わりのページなど）、`screenshots`（公開サイトの画面）。`status: "members-only"` の作品は部外者にはログイン画面になるので、主ボタンは traP の記事（なければ公開リポジトリ）にし、サイトは「サイト（部員向け）」として添えます。使用技術（`techStack`）は表示しません（歴代の cp20.dev のフレームワークだけ `editorial.ts` の `editions` から添える）。
- プロフィール（/about）：名乗りとリンク → 「速くしてきたもの」（性能改善5件を「どこで・何を・前→後」の切手で。押すとその経歴のダイアログ）→ 所属（名札。PC では2列）→ 経歴 → 好きなもの（音楽・漫画。本棚の背表紙の頭の絵は、1冊ずつ表紙を見て決めた位置から切り出す：`manga-covers.ts` の `face`・`zoom`。主人公の顔が横に欠けずに入り、目が絵の真ん中より少し上、題字・吹き出し・手の切れ端が入らない所）。画面について来る要素（sticky）は置かない。スマートフォンでは切手が横にすべる帯、音楽は2列。
- 経歴：`src/data/editorial.ts`。月と学年を併記。1行（`text`）は成果を書き、数字は `**…**` で太字（ISUCON のチーム名 [object Object] は、ほかの名前と同じく本文の書体のまま括弧なしで書き、改行しないよう間の空白をノーブレークスペースにする）。種類（`kind`）はルートの点に置く Lucide のアイコンで示す：受賞は朱のトロフィー（Trophy）、インターン（仕事）は藍の鞄（BriefcaseBusiness）、学校・プログラムは墨の角帽（GraduationCap）。トップの実績の付箋も同じアイコン（`src/components/Icon.tsx` の `KindMark`）。`id` がダイアログの id で、`/about#<id>`（例 `/about#isucon2026`）で開く（トップの実績が使う）。閉じると URL の `#` は外れ、フォーカスはその項目に戻る。`work` は関連作品（ダイアログからリンク）、`speedup` は「速くしてきたもの」の切手。各項目の詳しい説明（`detail`）は参加記や主催の発表にあることだけを書き、1行と切手の数字は `detail` にあるものだけ（`npm test` が照合）。資格は非掲載。
- フッター：リンクは `src/data/profile.json` の `links`（プロフィールと同じ）と RSS。QR コードのボタンは置かない。
- QR コード：スマホのヘッダーの右端のボタンで、cp20.dev の QR コードと大きな「cp20.dev」のダイアログを開く（`https://cp20.dev/#qr` で直接開く。対面で相手のスマホに読ませる用）。QR は `public/images/qr-cp20.svg` の静的ファイルで、`node scripts/build/qr.ts` が生成（サイトは QR のライブラリを持たない）。符号にするのは `https://cp20.dev/#<数字153桁>`（アドレスはバイト、数字は数字モード。バージョン5・誤り訂正 M）。数字のビットは誤り訂正の符号語を含めて全モジュールに GF(2) で線形に効くので、マスクを固定して連立一次方程式を解き（Russ Cox の QArt と同じ方法）、まん中のモジュールそのものでクローバー（緑）と、そのまわりの白を描く（3桁ずつの組が 1000 以上になったら、その組の最上位ビットを 0 に固定して解き直す）。8つのマスクのうちクローバーがいちばん描けるものを使う。誤りに頼らない普通の符号なので、読みやすさは落ちない。機能模様（位置・タイミング・位置合わせ・形式情報）は uqr が描いたものをそのまま使い、数字のないアドレスで uqr と同じモジュールになることを `npm test` が確かめる。数字の `#` はページが無視し、開いたときにアドレスから外す（`src/site/navigation.ts`）。`npm test` が生成結果との一致、クローバーのモジュールが絵のとおりであること、264px・132px に描いた絵をデコーダ（jsQR）で同じアドレスと読めることを検査し、`scripts/qa/browser-check.ts` はダイアログに表示された QR を撮って読み、そのアドレスでトップがダイアログもスクロールもなく開くことを確かめます。ボタンをスマホのヘッダーに置くのは、見せた流れのまま同じスマホで出せるように。
- 404：1行の説明、代表作3つ、作品一覧・プロフィール・記事へのリンク。`/works/` で始まるアドレスなら全作品の名前を並べる（静的な1ページなので、ブラウザでアドレスを見て切り替える）。
- 手動追加・除外・上書き：`src/data/manual.json`。
- スナップショット：`src/data/generated.json`。
- OG画像・アイコン・寸法：`src/data/previews.json`。OGがない作品にはテキストの代替を表示し、別の画像を捏造しません。ログインが必要で読めないページ（traP 部員向けのサービス）は、`works.json` に書いた画像（`image`）とアイコン（`icon`）を使います。`icon` と `image` はサイト内のパス（`/images/icons/…`・`/images/works/…`、`public/` にコミット）でもよく、そのまま表示します（anke-to v3 は traPtitech/logo のロゴの「a」の部分、NEON OVERDRIVE はサイトの favicon）。自作Cコンパイラは OG 画像が白地に題名だけなので、カードの絵 `public/images/works/c-compiler.png`（1200×630。大きな C、名前、clang → 1cc → 2cc → 3cc の世代、`int main() { return 42; }` とその LLVM IR、C で 4,842行・テスト165件、セルフホストの印。数字はリポジトリの `src/` と `test.sh` から）を一度描いてコミットし、`works.json` の `image` で指しています。HEAD を断るサーバーのアイコンは GET で確かめます。
- 音楽・漫画：`tracks.json` / `series.json`（定期処理が更新）。選定は2026版の元データで変更できます。
- 画像：`public/images/`、自動取得分は `public/media/`。92個の元URLを89ファイルに集約。`src/data/image-cache.json` が元URLとローカルファイルを対応付けます。漫画・YouTubeも事前保存し、ページに出典と著者・制作者を掲載。

画像は収集時に形式と15MB上限を検査し、内容ハッシュをファイル名に使用。新規取得に失敗した場合（新しいOG画像がSVG・15MB超・一時的な取得失敗など）は、前回の画像URL・寸法・ファイルを維持します。画像を含めてActionsからコミットし、ブラウザは同一サイトのStatic Assetsを参照。`/media/*` は長期キャッシュし、画像が変わるとURLも変わります。OG画像と音楽・漫画のサムネイルには幅320/640/960pxのWebP（元より2割以上狭いもののみ。縮小と再エンコードだけ）を、作品アイコンには幅96pxのWebPを `<元ファイル名>-<幅>w.webp` で作ります（元ファイルより小さくならないものは捨てる）。`public/images/covers` の表紙には幅240pxと原寸のWebPを、`public/images/works` の作品の絵にはスクリーンショットと同じ幅のWebPを作ります。いずれも `srcset`/`sizes`（アイコンは小さいWebPを直接）で配信します（`node scripts/sync/images.ts --variants-only` で取得なしに再生成。表紙や作品の絵を追加したら実行）。クライアントには `virtual:cp20-media`（`vite.config.ts`）としてローカルパスと寸法だけを渡します。SVGやHTMLを外部画像として保存しません。

`manual.json` の `articles` はURLで自動取得と合成、`overrides` はタイトル等を上書き、`exclude` は対象URLを非掲載、`projects` は作品を追加します。作品には `works.json` と同じフィールドを指定してください。

**作品のスクリーンショット**：`works.json` の `screenshots` に書いた画面（PC は1280×720、スマートフォンは iPhone 13 の2倍）を `npm run screenshots` が Playwright で撮り、`public/images/screenshots/<id>-<pc|mobile>.png` と WebP の縮小版（320〜960px と原寸）を書きます。どの画面を撮るかは `scripts/sync/screenshots.ts` にあります（フォームに入力して計算させるだけで、送信はしません）。定期処理では撮りません。画面は作品のページの上段に出します（カードは OG 画像）。PC の画面は作品の中身（ダイススペックの計算結果とグラフ、みんなのものさしのお題）の部分を 16:9 に切り抜いています。公開サイトのない自作Cコンパイラは、制作記事（trap.jp/post/2313）の見出し画像からエディタの部分を切り抜きます。それ以外の公開サイトのない作品は OG 画像のままです。

**共有したときの画像と説明**：`og:image` は `scripts/build/og.ts` がビルドのたびに描きます（アイコン、名前、`profile.json` の所属、トップの実績3つとその種類の Lucide のアイコン。文字はページと同じ書体（名前と実績は Yusei Magic、所属は Zen Maru Gothic）を HarfBuzz で輪郭にするので、ビルドする機械のフォントに左右されません）。説明（`description`）はページごとで、`src/site/route.ts` にあります。作品のページは作品の説明です。

**日本語の改行**：作品の説明・要約・成果・役割（`works.json`）と記事の題名は、ビルド時に BudouX（`word-break: auto-phrase` と同じ分かち書き）で文節の切れ目にゼロ幅スペースを入れ（`scripts/build/phrases.ts`、`vite.config.ts` から）、`word-break: keep-all` で折り返します。iPhone の Safari は auto-phrase を解釈しないため。ページに直接書いた文は `<wbr />` で区切ります。meta の説明などページの外に出す文は `plain()` で印を取ります。

**作品の追加方法**

1. `src/data/works.json`（または `manual.json` の `projects`）に作品を追加します。フィールドは既存の作品と同じです。`comments` の中のリンクは `[ラベル](https://…)` や `[ラベル](/works/<id>)` の形で書くとリンクになります（URLをそのまま書くと `npm test` が失敗します）。`id` はURL（`/works/<id>`）とシールの保存先（`pages/works--<id>`）になるため、英小文字・数字を1つずつのハイフンでつないだ形（例 `my-app-2`）にしてください。大文字・`.`・`--`・重複は `npm run build` と `npm run rules` がエラーで止めます。
2. `npm run rules` で `database.rules.json` を再生成し、作品の追加と一緒にコミットします。忘れると `npm test` とPRの `Firebase rules` ワークフローが失敗します（新しいページではシールを保存できないため）。
3. `main` にマージすると、サイトはCloudflareが、ルールは `Firebase rules` ワークフローが自動でデプロイします。

ページの一覧（固定ページの順番・タイトル・インデックスタブの順・URLの正規化・シールのページキー）は `src/site/pages.ts` にまとめてあり、ルーティング・ページ内遷移・タブ・プリレンダー・sitemap・DBルールはここから作られます。

## ページに貼れるシール

画面の右下にシール帳（クローバーと本人のアイコンの絵のシール2種類と、mixi2 のリアクションに倣った文字のシール10種類を6個ずつ2段に並べる）があります。閉じると右下の小さな「シール」タブになります（スマートフォンでは最初は閉じた状態）。シールを見るのは誰でもできますが、貼るには Google アカウントでのログインが必要です。

- 貼り方：シールをドラッグして好きな場所に落とす、またはクリック・タップで持ち上げてから貼りたい場所をクリック・タップ。シールにフォーカスしてEnter→矢印キー（Shiftを押しながらで大きく移動）→Enterでも貼れます。手に持ったシールはばねのように指・カーソルを追い、動く向きに傾き、離した位置からそのまま紙に貼り付きます。
- 自分のシール：クリック・タップで持ち上げ、もう一度クリック・タップした場所へ貼り直せます（ドラッグでも移動可）。持ち上げたままシール帳（閉じているときは右下のタブ）を押すか、シール帳へドラッグするとはがれます。マウスではホバーで出る×、キーボードでは×にフォーカスしてもはがせます。キーボードではシールにフォーカスしてEnter→矢印キー→Enterで動かせます（同じシールの位置だけを書き換えます）。Escapeで元の位置に戻ります。
- アイコン：貼ったシールにはその人の [Gravatar](https://gravatar.com/) アイコンが添えられ、シールにホバー（タッチではタップ）すると表示されます。DBに保存・公開されるのはGoogleアカウントのメールアドレスから作るSHA-256ハッシュ（Gravatarの仕様）だけで、メールアドレスや名前は保存しません。Gravatar未登録の人は自動生成の模様になります。シール帳の説明は未ログイン時の1行（「ログインすると、シールを貼れます。貼ったシールはみんなに見えます。」）だけで、未ログイン時は「Google でログイン」ボタンとその1行と薄く表示したシール、ログイン中は自分のアイコン（Gravatarの設定へのリンク）と、このページで貼れる残り枚数を表す5つの丸を表示します。エラーのときだけ文章で知らせます。
- 他の人のシールはポインタを受け取らないので、上に重なっていてもその下のリンクやボタンへのクリック（Ctrl・中クリック、右クリックのメニュー、セレクトを含む）はそのまま届きます。誰が貼ったかはホバー（タッチではタップ）で表示。右のインデックスタブにかかる位置のシールはページ内側に寄せて描きます。
- 貼ったシールは紙に押さえられたあと一度だけ動きます（「すき」「エモ」「かわいい」は脈打ち、「おめでと」は光を出して跳ね、「なるほど」「わかる」「学び」はうなずき、ほかは跳ねる。整理した絵のシールも、動かしたときは元のとおりハートは脈打ち、目はまばたき、きらきらは光を出し、いいねはうなずく）。自分が貼った・動かしたときだけで、ほかの人のシールや読み込み時は動きません。動きを減らす設定では動きません。
- 文字のシール（`public/stamps/suki.svg` など）は mixi2 の日本語のリアクションに倣ったもので、ポップな丸文字の Mochiy Pop One（SIL OFL）の字形を少し太らせて角を丸め、アウトライン化して描いています（実行時にフォントは読み込みません）。語は mixi2 のリアクションにある日本語の言葉から、紹介記事（ITmedia NEWS 2025-01-15、Appllio「mixi2の使い方」のリアクション一覧の画面）で確かめたポジティブなものだけを選んでいます：「すき」「なるほど」「ありがと」「エモ」「わかる」「学び」「えらい」「かわいい」「おつかれ」「おめでと」（表記も mixi2 のとおり）。mixi2 と同じく台紙や墨の線はなく、1語1色（すきはピンク、なるほどはコーラル、ありがとはティール、エモはラベンダー、わかるは若葉、学びは青、えらいは山吹、かわいいは藤色がかったピンク、おつかれは水色、おめでとは赤。上が少し明るいグラデーション）の文字を白い台紙で型抜きし、4文字の語は2文字ずつ2行、2文字・3文字の語は縦長に詰めて1行で組みます。シール帳では同じような色が上下左右に隣り合わないように並べます。mixi2 の画像・字形・商標は使っていません（言葉と配色の雰囲気だけ）。
- 種類の番号（DBの `kind`）は `src/stamps/sticker-kinds.ts` の並び順で、保存済みのシールが指すため詰めたり並べ替えたりしません。シール帳から外した種類（いいね・きらきら・見てる・ハートの絵のシール）は `retired` として番号と絵を残し、すでに貼られたものは表示され、動かす・はがすこともできます。シール帳に並べる種類と順番は `SHEET_KINDS`。種類を足したら `npm run rules` で DB のルールを再生成します。
- 取り消し（最後に貼ったものをはがす）・非表示（初期状態は表示）・シール帳の開閉ができます。削除は保存待ちでも即時反映します。

- Firebaseプロジェクト：**general**（ID `cp20-platform`）。
- 専用Realtime Database：`cp20-platform-portfolio-stamps`（`asia-southeast1`）。
- URL：`https://cp20-platform-portfolio-stamps.asia-southeast1.firebasedatabase.app`。
- 専用Webアプリ：`cp20.dev definitive`。設定は `src/data/firebase.json`。ブラウザ用の公開設定であり、管理キーではありません。
- 既存の他のDBは変更していません。

**公開前に必要な設定（Firebase Console）**

1. Authentication → Sign-in method で **Google** を有効化。
2. Authentication → Settings → 承認済みドメインに `cp20-definitive.cp20.workers.dev` と `cp20.dev`（開発時は `localhost`）を追加。
3. Actionsの `Firebase rules` ワークフロー（`main` へのマージで自動、または Run workflow）で `database.rules.json` をデプロイ（Google ログインのみ書き込み可・`avatar` 項目の検証を含む）。ファイルがページ一覧や `main` と食い違っている、またはエミュレーターでの検証に失敗したときはデプロイせずに止まります（手動の `npm run firebase:rules` も同じ。下記「ルールの更新」）。

Firebase Auth（Googleのポップアップログイン）でログインしたUIDの領域だけ書き込み・削除を許可します。ルールで `auth.token.firebase.sign_in_provider == 'google.com'` を必須にしているため、匿名認証などでは書き込めません。1ページ・1人あたり5つ、6つ目から古いものを置き換え（貼り直しは同じ枠の位置だけを書き換えるので、ほかのシールは消えません）。表示は更新が新しい100人分（最大500個）に制限し、絞り込みなしの公開読込は拒否します。座標・種類・角度・タイムスタンプ・Gravatarハッシュ（64桁の16進数）・項目をDBルールで検証し、1秒未満の連続更新を拒否。間隔は削除しても残る `throttle/$uid` で数え、レコードの書込はその更新と同時（`updatedAt` も毎回サーバー時刻）でなければ拒否するため、子パスへの部分書込や削除→再作成でも回避できません。古いUIDのレコードは自動削除しません。

Web標準のEventSourceでFirebase RESTストリームへ直接接続。非表示タブでは購読を休止し、再表示時に最新データへ接続します。Auth SDKはシール帳に触れたとき（以前ログインした人はページ表示後）に遅延読込し、ログインのポップアップがクリック内で開けるようにしています。保存はレコードと `throttle/$uid`（最終書込時刻）を同時に更新するRESTのマルチパスPATCHで、`throttle` の前回値を照合（compare-and-swap）して同時編集を検出します。受信したストリームの描画は最大で毎秒4回にまとめ、シールの位置は基準要素ごとに1回だけ測ります。貼る・動かす・はがすはネットワーク応答を待たず即時反映し（楽観的更新、`src/stamps/optimistic.ts`）、保存は1件ずつ、前の保存の完了から1.1秒あけて送ります（DBの1秒間隔制限に合わせた直列のPromiseチェーン）。保存に失敗した操作はその場で取り消して「保存できませんでした」と表示し、再試行はしません。別タブと同時に書いた場合も、compare-and-swapで拒否された側が取り消されます。購読を休止しても保存は独立して完了し、各リクエストに15秒の通信タイムアウトを設けています。ネットワークの切断はブラウザ自身が再接続し、ブラウザが諦めたとき（HTTPエラーなど）だけ「シールに接続できません」と伝えて5秒後に開き直します。ページ遷移・記事の年の切り替え・作品切替はブラウザ内、定期収集はGitHub Actions、HTML/CSS/JSはStatic Assetsで完結し、サイト独自のWorker APIはありません。

ルールの更新：`database.rules.json` は手で編集せず、`npm run rules` で生成してコミットします（元は `scripts/firebase/rules.ts`・`src/site/pages.ts`・`src/stamps/limits.ts`。生成結果とのずれは `npm test` で検出）。`main` で `database.rules.json` が変わると、Actionsの `Firebase rules` がエミュレーターで検証してから専用DBへデプロイします（PRでは検証のみ）。リポジトリのSecretsに `FIREBASE_SERVICE_ACCOUNT`（cp20-platformの「Firebase Realtime Database 管理者」ロールを持つサービスアカウントのJSONキー）を登録しておきます。手元からは、Firebase CLIでログインして `npm run firebase:rules`。サイト（Cloudflare）とルールは別々にデプロイされるため、書込形式が変わる変更ではマージ直後の数分間、シールの保存が失敗することがあります。`.firebaserc` は専用DBだけを指します。レコードの管理・削除はFirebase Consoleの専用DBから行えます。

## UI / Web標準

SolidJS 2の `createSignal`、ドラフト形式の `createStore`、派生値の `createMemo`、Context、`For` / `Show`、2引数の `createEffect`、`onSettled` を使用。全UIをTSXで記述し、公式 `@solidjs/vite-plugin` のSSR出力をビルド時にHTML化します。配信対象は `dist/client` のみです。

記事は結果領域、スタンプは状態メッセージの領域を確保し、スクロールバー分の幅も保持します。書体は役割で3つ：見出し・名前・ラベル・ボタン・数字は手書きの Yusei Magic、文は Zen Maru Gothic、コード・リポジトリ名・行き先のアドレスは IBM Plex Mono SemiBold（下記の cp20 Mono）。記事画像の枠は16:9で統一し、元画像は切り抜かず収めます。画像は切手の白い余白と目打ちで囲み、元の色と比率を保持します。

`npm test`（`vitest run`）は外から観測できる振る舞いだけを検査します。純粋なロジックは使う機能のフォルダ（`src/stamps` など）に置き、テストはその隣（`foo.ts` の隣に `foo.test.ts`）に置きます。DOM・Firebase・データファイルに触れるファイル（コンポーネントや `createXxx`）と触れないファイル（`layout.ts`・`record.ts`・`optimistic.ts`・`works.ts` など）を分け、後者を Node で直接テストします。`createXxx` はシグナルを作るため、それを持つコンポーネントの中で同期的に呼びます。fetch・時計・EventSource・ファイルの置き場所（`scripts/sync` の収集は `dirs` で一時ディレクトリを受け取る）は引数で渡す小さなテストダブルに差し替えるので、テストは速く決定的で、グローバルを書き換えません（そのためテストファイルはワーカーを共有します。`isolate: false`）。コミットされたデータ（収集したスナップショット、works.json、経歴、表紙など）の約束は `src/data/snapshot.test.ts` に、ビルド結果（`dist/client`）の約束は `scripts/build/dist.test.ts` にまとめ、どちらも1つの約束を1テストにして違反をすべて並べます。ソースコードの文字列を照合するテストや、ライブラリ自体を確かめるテストは置かず、見た目や操作は下記のブラウザ検証で確かめます。テスト名は仕様として読める日本語の文で、アサーションは `node:assert/strict` です。CSSの約束事（px指定のfont-sizeを使わない、印刷用スタイル、シールの層の解放）はレビューで見ます。`dist.test.ts` は `dist/client` がなければスキップするため、`npm run verify` の中で走らせてください。シールの保存失敗の取り消し（`store.ts` の配線）はブラウザ検証でだけ確かめており、`npm run verify` には含まれません。
